# PinTrip MVP 產品規格

## 0. 文件狀態

- 專案名稱：PinTrip
- 專案類型：旅遊地點收藏地圖 MVP
- 文件用途：定義產品目標、MVP 範圍、核心規則與驗收條件
- 最後更新：2026-07-30

本文件是產品需求的規範來源。技術架構、服務選擇、資料流、路由與實作細節記錄於 `docs/ARCHITECTURE.md`。

## 1. 產品問題與目標

使用者準備旅行時，常會在 Instagram「我的珍藏」保存美食、咖啡廳、景點、購物店家與旅遊攻略。真正整理地點時，仍需逐篇開啟貼文、辨認店名與地址、搜尋實際地點，再加入地圖工具並排除重複內容。

PinTrip 要將單篇 Instagram 貼文中的旅遊資訊，轉換成可確認、可分類、可篩選並能顯示於地圖的地點收藏。MVP 要驗證：在收藏貼文時逐步整理地點，是否能減少旅行前的重複工作。

### 1.1 目標使用者

- 習慣從 Instagram 蒐集旅遊資訊的人。
- 會依城市、目的地或旅行主題建立珍藏分類的人。
- 規劃旅行時，需要重新整理店名與地址的人。
- 想把美食、景點與購物地點集中在同一張地圖的人。

MVP 以個人使用為主，不支援多人共同編輯。

---

## 2. 核心用語

### 2.1 旅行收藏（Trip）

使用者依目的地或旅行主題建立的地點收藏容器，概念接近 Instagram「我的珍藏」。

旅行收藏不是每日行程，不包含出發日期、結束日期、交通安排或路線規劃。文件中的產品用語統一使用「旅行收藏」；技術資料概念保留 `Trip`。

### 2.2 候選地點（ImportItem）

系統從一次貼文匯入中辨識出的單一地點候選。候選資料必須經使用者確認或拒絕，不能直接成為正式收藏。

### 2.3 實際地點（Place）

由外部地點服務提供、具有可識別身分與地圖位置的地點。正式收藏必須先匹配並選定一筆實際地點。

### 2.4 正式收藏地點（TripPlace）

使用者確認後，加入特定旅行收藏的實際地點。同一旅行收藏與同一實際地點的組合只能有一筆正式收藏地點。

---

## 3. 核心產品原則

1. 一篇貼文可以產生零個、一個或多個候選地點。
2. AI 與系統辨識結果只能作為候選資料。
3. 每個候選地點都必須由使用者確認或拒絕。
4. 只有確認且匹配實際地點的項目才能成為正式收藏並顯示在地圖。
5. 同一旅行收藏中的相同實際地點只能有一筆正式收藏與一個地圖標記。
6. 同一正式收藏地點可以保留多篇來源貼文。
7. 自動取得貼文內容失敗時，必須提供手動補充流程，不得假裝解析成功。
8. 卡片清單與地圖必須使用相同的分類篩選結果。
9. 使用者只能存取與操作自己的旅行收藏及其相關資料。

---

## 4. 核心使用流程

1. 使用者以 Google 登入 PinTrip。
2. 使用者建立旅行收藏，例如「東京咖啡」或「京都秋季旅行」。
3. 使用者從支援的 Android 裝置分享單篇 Instagram 貼文至 PinTrip，或在 Web 介面貼上單篇貼文網址。
4. 使用者選擇目標旅行收藏。
5. PinTrip 建立匯入任務，並嘗試取得可讀取的來源內容。
6. 系統解析零個、一個或多個候選地點。
7. 系統嘗試為每個候選地點比對實際地點。
8. 使用者逐一修改、確認或拒絕候選地點。
9. 已確認的地點加入旅行收藏；重複地點只增加新的來源關聯。
10. 使用者在卡片清單與地圖查看正式收藏，並依分類篩選。

## 5. MVP 功能範圍

### 5.1 Google 登入

- Google 是 MVP 唯一的登入方式。
- 支援登入與登出。
- 不實作帳號密碼、公開註冊、信箱驗證或密碼重設。
- 每位使用者只能查看與管理自己的旅行收藏、匯入、候選地點、正式收藏與補充資料。

具體 Authentication 套件、Session 機制與部署設定由 `docs/ARCHITECTURE.md` 記錄。

### 5.2 旅行收藏管理

使用者可以：

- 建立旅行收藏。
- 輸入及修改收藏名稱與目的地名稱。
- 查看自己的旅行收藏列表。
- 進入單一旅行收藏。
- 刪除旅行收藏。

刪除旅行收藏時，必須先清楚提示影響範圍。確認刪除後，應移除該旅行收藏所屬的匯入、候選項目、補充截圖、正式收藏及來源關聯；共享的外部實際地點資料不因此刪除。

### 5.3 貼文匯入

使用者可以透過以下方式建立匯入：

- 從支援 Web Share Target 的 Android 裝置分享單篇 Instagram 貼文網址或分享文字。
- 在 Web 介面手動貼上單篇 Instagram 貼文網址。
- 貼上分享時附帶的文字內容。

每筆匯入必須：

- 屬於一位使用者與一個旅行收藏。
- 保留原始來源網址。
- 保留可取得的來源文字或必要資料快照。
- 顯示目前處理狀態。
- 記錄可供使用者理解的失敗原因。

### 5.4 手動補充資料

當來源內容不足時，使用者可以補充：

- 貼文文字。
- 貼文截圖。
- 店名或景點名稱。
- 地址或區域。
- 其他有助於辨識的資訊。

截圖上傳是 MVP 必要能力。圖片儲存方式、保存期限與解析實作屬於架構決策；刪除所屬旅行收藏時，相關截圖也必須刪除。

手動資料只用於重新解析或搜尋實際地點，不能繞過實際地點比對直接建立 `Place`。

### 5.5 匯入狀態

每筆 Import 使用以下狀態：

| 狀態 | 語意 |
| --- | --- |
| `received` | 已收到匯入資料，尚未開始分析 |
| `processing` | 正在取得來源、分析內容或重新處理 |
| `needs_input` | 資料不足或沒有候選地點，等待使用者補充或結束處理 |
| `review_required` | 已有候選地點，且至少一筆尚未確認或拒絕 |
| `completed` | 所有候選項目都已確認或拒絕，或使用者已結束零候選匯入 |
| `failed` | 發生目前無法繼續的技術錯誤 |

狀態規則：

- 解析出候選地點後進入 `review_required`。
- 只要仍有候選地點未確認或未拒絕，就維持 `review_required`。
- 所有候選地點都已處置後進入 `completed`；`completed` 不代表所有候選都被收藏。
- 零候選地點先進入 `needs_input`。使用者可補充資料後重試，或選擇「沒有可用地點／結束處理」，使 Import 進入 `completed`。
- `failed` 與 `needs_input` 在重新嘗試時回到 `processing`。
- 使用者必須能從介面得知目前狀態及下一個可採取的動作。

### 5.6 AI 地點解析

系統應嘗試從可取得的來源與補充資料辨識：

- 地點名稱。
- 固定分類。
- 城市或區域。
- 地址文字。
- 簡短介紹。
- 推薦品項。
- 用於搜尋實際地點的關鍵字。
- 辨識信心程度。

每個辨識地點建立獨立候選項目，並保留相同來源 Import。不得只保存第一個辨識結果。

### 5.7 實際地點比對與確認

候選實際地點可能包含：

- 正式名稱。
- 完整地址。
- 城市或區域。
- 經緯度。
- 地圖連結。
- 外部地點識別碼。

使用者可以針對每個候選地點：

- 查看來源貼文、AI 結果與實際地點候選。
- 修改名稱、分類、介紹與推薦品項。
- 重新搜尋或補充資料。
- 選擇正確的實際地點並確認加入旅行收藏。
- 拒絕該候選地點。

若仍無法匹配外部實際地點，候選項目不得成為正式收藏或地圖標記。MVP 不支援純手動建立 `Place`。

### 5.8 正式收藏與去重

正式收藏地點至少保存：

- 所屬旅行收藏。
- 實際地點。
- 固定分類。
- 說明。
- 推薦品項。
- 使用者備註。
- 確認時間。
- 一個或多個來源 Import。

重複匯入規則：

- 使用者確認候選項目對應既有實際地點後，不建立第二筆正式收藏或地圖標記。
- 新的來源 Import 關聯至既有正式收藏。
- 新解析出的分類、說明、推薦品項或備註不得自動覆蓋既有內容。
- 系統可顯示新舊差異，但只有使用者明確選擇後才能更新。
- 地點是否相同，優先依外部地點識別碼判斷。

### 5.9 卡片、地圖與分類篩選

旅行收藏頁面提供卡片清單與地圖模式。

每張卡片至少顯示：

- 地點名稱。
- 分類。
- 地址或區域。
- 簡短說明。
- 推薦品項。
- 來源數量。
- 地圖或詳細資料入口。

地圖至少支援：

- 只顯示已確認的正式收藏地點。
- 不同分類使用不同圖示或視覺標記。
- 點擊標記後查看地點簡要資訊。
- 與卡片清單共用相同篩選狀態。

MVP 固定使用以下分類：

- `food`
- `cafe`
- `attraction`
- `shopping`
- `other`

每個正式收藏地點只有一個分類。使用者可選擇一個或多個分類；選擇多個分類時，只要符合其中任一分類就顯示。MVP 不包含一般關鍵字搜尋。

### 5.10 匯入紀錄

使用者可以查看：

- 來源貼文。
- 所屬旅行收藏。
- 匯入時間與狀態。
- 解析出的候選地點數量。
- 失敗原因與待補充資訊。
- 尚未處置的候選項目。

`failed` 與 `needs_input` 匯入可以重新嘗試。

## 6. 平台範圍

### 6.1 響應式 Web

MVP 必須提供可在桌面瀏覽器、Android 手機瀏覽器與 iPhone Safari 正常查看及操作的響應式 Web 介面。

### 6.2 Android PWA

Android MVP 必須：

- 可由支援的 Android 瀏覽器安裝為 PWA。
- 提供 Web Share Target，接收 Instagram 分享流程實際提供的網址或文字。
- 在分享資料不足時，引導使用者補充資訊。

PWA Share Target 能接收的內容取決於作業系統、瀏覽器與來源 App；不得假設一定能取得完整貼文文字、圖片或登入後內容。PWA 不代表 MVP 必須支援完整離線操作。

### 6.3 iOS

iOS MVP 不實作原生 Share Extension。第一版使用者在 Instagram 複製單篇貼文連結，再於 PinTrip 貼上並選擇旅行收藏。

## 7. 核心資料概念

本節定義產品關係，不指定資料庫實作方式。

- `User`：PinTrip 使用者，可擁有多個 Trip。
- `Trip`：旅行收藏，可包含多筆 Import 與 TripPlace。
- `Import`：一次單篇貼文匯入任務，保存來源、狀態、可取得資料與錯誤資訊。
- `ImportItem`：Import 產生的單一候選地點，可被修改、確認、拒絕或比對至 Place。
- `Place`：外部地點服務中的實際地點，包含名稱、地址、座標、外部識別碼與地圖連結；本身不代表使用者已收藏。
- `TripPlace`：Place 經使用者確認後加入特定 Trip 的正式收藏，保存該收藏專屬的分類、說明、推薦品項、備註與確認時間。
- `TripPlaceSource`：TripPlace 與來源 Import 的關聯，使一筆正式收藏可以保留多篇來源貼文。

同一 Trip 與 Place 的組合只能有一筆 TripPlace。

---

## 8. Instagram 來源限制

PinTrip MVP 不把 Instagram Saved Posts、Saved Collections 或私人收藏資料夾視為可由官方 API 直接同步的資料來源，因此不支援：

- 登入 Instagram 後自動同步私人珍藏。
- 貼上 Saved Collection URL 後整批匯入。
- 在背景定期掃描 Instagram 新珍藏。

單篇貼文能取得多少內容，取決於公開狀態、登入要求、貼文類型、隱私設定及分享來源提供的資料。PinTrip 不得要求 Instagram 密碼，也不得把不穩定爬蟲作為唯一可用流程。

Instagram 公開內容的實際取得方式仍是未決架構事項；無論採用何種方式，都必須保留手動補充流程。

## 9. MVP 非目標

- Instagram Saved Collections 自動同步。
- Instagram 私人貼文完整讀取。
- 要求使用者提供 Instagram 密碼。
- 帳號密碼登入及密碼管理。
- 純手動建立無外部匹配的 Place。
- 一般關鍵字搜尋。
- 多人共同編輯旅行收藏。
- 社群貼文、公開清單、追蹤或按讚。
- 個人化推薦演算法。
- 自動產生每日行程、路線最佳化或交通時間安排。
- 預算、訂房或票券整合。
- 完整離線地圖與推播通知。
- 原生 Android App、原生 iOS App 及原生 iOS Share Extension。
- 桌面瀏覽器擴充功能。
- 整批匯入 Instagram 資料匯出檔案。

未列入 MVP 的功能，不得因未來可能使用而提前實作。

## 10. 驗收條件

### 10.1 身分與資料隔離

- 使用者可用 Google 登入及登出。
- 不同使用者不能查看或操作彼此的資料。

### 10.2 旅行收藏

- 使用者可建立、查看及修改旅行收藏。
- 使用者確認後可刪除旅行收藏及其所屬資料。

### 10.3 匯入與平台

- 使用者可手動貼上單篇 Instagram 貼文網址並選擇旅行收藏。
- Android 使用者可安裝 PWA，並透過 Web Share Target 將支援的網址或文字送至 PinTrip。
- 每次匯入都建立可查看狀態與失敗原因的紀錄。

### 10.4 多地點與失敗補充

- 一篇貼文可產生多筆可獨立處置的候選地點，且不得只保存第一筆。
- 來源不足時可補充文字、截圖、名稱或地址後重新嘗試。
- 零候選匯入可補充後重試，或由使用者主動結束。
- 技術失敗不會顯示為成功，且可查看原因並重新嘗試。

### 10.5 確認與實際地點

- AI 結果不會直接進入正式收藏。
- 使用者可修改候選內容、選擇外部實際地點、確認或拒絕。
- 未匹配外部實際地點的項目不能成為正式收藏。

### 10.6 正式收藏、地圖與篩選

- 已確認地點出現在卡片與地圖，未確認地點不出現在正式地圖。
- 多分類篩選以任一分類符合為準，並同步影響卡片與地圖。
- 相同 Trip 與 Place 不產生重複正式收藏或地圖標記。
- 重複匯入可增加來源，但不能自動覆蓋既有內容。

### 10.7 狀態

- Import 狀態符合第 5.5 節定義。
- 仍有未處置候選時不能顯示為 `completed`。
- `completed` 可以包含被拒絕的候選，也可以是不含候選的使用者主動結束結果。

## 11. MVP 完成定義

以下流程是核心旅程里程碑：

> 建立旅行收藏 → 匯入一篇貼文 → 解析一個或多個地點 → 使用者確認 → 加入正式收藏 → 在卡片與地圖查看及篩選。

核心旅程可運作不等於 MVP 已完成。只有第 10 節所有適用驗收條件都通過，才能宣告 MVP 完成。

MVP 不要求所有 Instagram 貼文都能自動解析成功；但自動取得失敗、手動補充、重新嘗試與誠實呈現狀態的流程本身必須通過驗收。

MVP 要驗證：

1. 使用者是否願意把貼文送進 PinTrip。
2. 結構化地點是否能減少旅行前的整理時間。
3. 多地點解析與確認流程是否容易使用。
4. 卡片與地圖是否比 Instagram 珍藏更方便查找地點。
5. 自動讀取失敗時，手動補充流程是否仍具有使用價值。

## 12. 交由架構文件決定的事項

以下產品能力或限制已決定，但具體實作仍由 `docs/ARCHITECTURE.md` 記錄：

- Google 登入所使用的 Auth 套件、Session 與部署設定。
- Android PWA 與 Web Share Target 的實作方式。
- 外部地點比對與地圖呈現方式。
- AI 解析、背景處理與重新嘗試方式。
- 截圖儲存、保存期限與刪除機制。

以下技術方案尚未指定：

- 資料庫服務。
- Authentication 套件或服務。
- 地圖服務與 Places API。
- AI 模型與供應商。
- 背景任務服務。
- 圖片儲存服務。
- UI 元件庫。
- 狀態管理方案。
- 測試框架。
- 部署與環境配置。
- Instagram 公開內容的實際取得方式。

在正式決定前，Agent 不得自行選擇、安裝或把任何候選方案寫成既定架構。
